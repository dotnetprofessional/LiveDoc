- **2026-07-18**: Design review — automatic post-run coverage in Visual Studio Test Explorer. **Root cause is structural, not config:** VSTest `ITestLogger` extensions (our `LiveDocCoverage` logger) only run under `vstest.console`/`--logger`; they are NOT activated in **design mode** (Test Explorer, VS Code Test Explorer), so `<LoggerRunSettings>` and the `VSTestLogger` MSBuild property do nothing in the IDE even though logger *discovery* succeeds. **The design-mode-capable extension point is a data collector `IDataCollectorAttachmentProcessor`** (vstest-docs RFC 0031 — attachments processing runs in "both design mode and command line"; "Analyze Code Coverage" runs vstest.console in a variation of design mode). Verified in vstest source: (1) `DataCollectorAttachmentsProcessorsFactory.Create` loads processors ONLY from **invoked** data collectors carrying `[DataCollectorAttachmentProcessor]` — standalone processors are not discovered, so we must ship our own collector to host it; (2) `TestRunAttachmentsProcessingManager` routes attachments **purely by URI** (`attachments.Where(a => uris.Any(u => u.Equals(a.Uri)))`), so a LiveDoc-owned processor returning `datacollector://Microsoft/CodeCoverage/2.0` receives Microsoft's `.coverage` regardless of who owns the profiler. **Activation without repo-specific runsettings:** the per-project MSBuild property `RunSettingsFilePath` (settable from NuGet `build/*.targets` or Directory.Build.props) IS honored by Test Explorer and overrides the solution runsettings (learn.microsoft.com "Configure unit tests by using a .runsettings file" → Set a build property). Solution-root `.runsettings` autodetect is only a fallback (requires Tools>Options>Test *Auto detect runsettings files* ON; not packageable). **Extra win:** a data collector implementing `ITestExecutionEnvironmentSpecifier.GetTestExecutionEnvironmentVariables()` can inject `LIVEDOC_RUN_METADATA_DIR` into the testhost, deterministically fixing the reporter/consumer metadata-dir mismatch. **Constraints:** DataCollector DLL must be named `*collector.dll` (platform discovery optimization); `Uri.Equals` is path-case-sensitive so the CodeCoverage URI casing must be exact. **Open assumption before build:** whether a *single-project* Test Explorer coverage run triggers attachment processing for a third-party processor — smallest experiment is a throwaway `*collector.dll` sentinel processor claiming the CodeCoverage URI, activated via `RunSettingsFilePath`, run under "Analyze Code Coverage for All Tests". Decision: `.squad/decisions/inbox/mal-vstest-coverage-activation.md`.

- **2026-07-18**: Facilitated post-rejection retrospective for the VSTest coverage collector (Simon authored, locked out; Wash owns revision). **Two blockers, both from implicit contracts in my design.** (1) An auto-set MSBuild `<VSTestLogger>LiveDocCoverage;RunMetadataDir=…</VSTestLogger>` aborts *every* plain `dotnet test` — MSBuild treats `;` as its item-list separator, so it becomes two loggers and the bogus second one throws a fatal `CommandLineException`. **Durable rule:** never place a vstest `name;k=v` logger string into an MSBuild property; deliver runtime config via runsettings `RunConfiguration.EnvironmentVariables` (no separator) — the data collector already injects `LIVEDOC_RUN_METADATA_DIR` into testhost, so the CLI logger's `RunMetadataDir` param is redundant. The attachment processor is the single upload authority (design mode + CLI); do **not** auto-enable the CLI logger (double-processing + abort risk). (2) `SupportsIncrementalProcessing => true` is a real contract: the processor may get attachment **subsets** across rounds and MUST carry state forward via its **return value**. Simon read the marker only from the current call and dropped the marker set from the return → in "Analyze Code Coverage for **All** Tests" the marker and `.coverage` land in different rounds → permanent silent skip presented as a safe `LD-COV-043`. **Resolution:** set `SupportsIncrementalProcessing => false` (guaranteed single full-set call), but make correctness batch-independent anyway — always return inputs unchanged, discover markers from **disk** under the metadata root, iterate **all** markers/dirs (never `FirstOrDefault`, else multi-project silently covers one project). **Idempotency contract:** per-`runId` sentinel written **only** on HTTP 2xx; a failed upload never sentinels and stays retryable — no diagnostic may present a not-done upload as a safe skip. **Lifecycle identity:** compute the invocation metadata dir once behind a shared accessor so `Initialize` and `GetTestExecutionEnvironmentVariables` can't diverge regardless of call order. **Diagnostic honesty:** HTTP 2xx only proves server-accepted + persistence-scheduled + WS-broadcast-enqueued (server 404-guards missing runs, `attachCoverage`→`saveRun`+broadcast, REST hydrates late viewers) — it does NOT prove viewer display; the processor must never emit a viewer-display claim (`LD-COV-090` is E2E-only). **Process learning:** any change that flips a default to on-by-default (coverage via `RunSettingsFilePath`) must ship a "plain `dotnet test` still passes" regression *before* review; design docs must pin incremental semantics, idempotency/retry, multi-marker correlation, invocation-dir single-source-of-truth, and diagnostic-honesty contracts explicitly, or implementers guess. Correction: `.squad/decisions/inbox/mal-coverage-rejection-retrospective.md`.

- **2026-07-18**: Re-opened and corrected the VSTest attachment-processor lifecycle contract after the `SupportsIncrementalProcessing => false` mandate proved unusable. **Decisive source fact:** VSTest **refuses to run** non-incremental attachment processors — `TestRunAttachmentsProcessingManager.ProcessAttachmentsAsync` gates with `if (!SupportsIncrementalProcessing) { logger.SendMessage(Error, "Non incremental attachment processors are not supported"); continue; }`, so a `false` processor performs **zero work** in *both* CLI and VS design mode (they share the one manager; `Analyze Code Coverage for All Tests` = vstest.console in a design-mode variation, RFC 0031 §4). RFC 0031 states verbatim *"Current implementation doesn't support non incremental processing so `SupportsIncrementalProcessing` should be `True`"* — the `false` branch is documented-but-unimplemented. Made a hard requirement in microsoft/vstest **PR #4280** / issue **#4325**; MS's own `CodeCoverageDataAttachmentsHandler` is `=> true`. **Durable rules:** (1) LiveDoc's `LiveDocCoverageAttachmentProcessor` MUST be `SupportsIncrementalProcessing => true`; `false` is inert, and any "CLI fallback proven" evidence under `false` validated the *logger*, not the processor. (2) `true` requires `ProcessAttachmentSetsAsync` to be **associative/idempotent** because the platform MAY re-feed a prior round's output as input (`ProcessAttachmentSetsAsync(prevResult.Concat(new))`); our HTTP-POST side effect is made associative by the **disk per-runId sentinel** (write only on 2xx, skip if present, never sentinel a failure). (3) **Processor instances are re-created every round** (`DataCollectorAttachmentsProcessorsFactory.Create` per processing request, disposed after) — **no in-memory field survives**; marker discovery, run correlation, and idempotency must be **disk-only**. (4) **Disk-marker freshness must be judged by file completion/last-write time, NOT `InitializedAtUtc`** — for long-running suites the collector `Initialize` time is legitimately far older than processor construction, so an `InitializedAtUtc`-based staleness reject wrongly discards valid markers (Correction A: remove that reject; trust attachment-delivered markers at any age). (5) The manager routes attachments **purely by `GetExtensionUris()` URI**, so a LiveDoc-owned processor advertising `datacollector://microsoft/CodeCoverage/2.0` receives Microsoft's merged `.coverage` regardless of profiler ownership — third-party correlation is supported; no mechanism change needed. **Process learning:** never mandate an extension-point flag value from an RFC's *documented behaviour* without checking the *implementation* — the RFC's `false`-single-call semantics never shipped; the retrospective's `false` choice inherited that gap. Correction: `.squad/decisions/inbox/mal-incremental-processor-correction.md` (supersedes D2 of the retrospective and the matching clause in `wash-coverage-revision.md`).
